# LAB_VALIDATION.md

## Regra

O projeto deve operar como laboratorio: testar, validar, refinar, testar novamente e somente entao registrar checkpoint. Nada de chute. Laboratorio significa publicação bloqueada e evidência permanente, não dado descartável nem pausa operacional.

## When done P0

Antes de qualquer promoção pública, calcular `current_public_indexable_count` com páginas jurídicas aprovadas em `published_manifest`, indexáveis e verificadas; páginas institucionais não contam para o marco jurídico. Calcular `deficit_to_10000 = max(0, 10000 - current_public_indexable_count)`. A variável `deficit_to_10000` governa o tamanho máximo da promoção pública do marco. P0 não pode passar para P1 enquanto o déficit for maior que zero, nem enquanto houver spam, thin content, duplicidade, fonte ampla mascarada, revisão pendente, CTA/paid-intent indevido, HTML pesado, sitemap/canonical/robots incorreto ou smoke HTTP/Googlebot ausente.

O laboratório pode gerar backlog bloqueado acima do déficit para provar escala, mas promoção pública do marco deve ser limitada pelo déficit calculado e pelos gates completos. Se os dados vivos mostrarem `current_public_indexable_count=0`, a próxima macrocamada deve aumentar capacidade real de conteúdo jurídico autoral e publicação segura, não repetir diagnóstico já materializado.

Laboratorio deve usar engenharia agressiva inteligente. O agente deve planejar a hipótese do ciclo, rodar validação em massa quando o escopo for massa, usar CPU disponível para acelerar prova e refinar algoritmo antes de expor qualquer conteúdo público. Passividade, pergunta desnecessária, commit sem autocrítica e validação pequena para decisão massiva são falhas de laboratório.

A ferramenta de agentes está sempre disponível e é obrigatória neste `/goal` quando houver frente independente real de revisão, performance, integração, causa raiz, validação proporcional ou risco P0; ausência de subagente exige prova de tarefa trivial sem frente paralela útil, não preferência operacional.

Antes de cada ciclo, checkpoint, documentação relevante ou commit, o agente deve ler o contexto atual do repo, contratos e dados reais. teste verde não substitui leitura dos dados reais, JSONL, amostras e diff. O ciclo deve preferir macrocamada vertical que conecte dados, fonte, revisão, manifesto, render, crawl/sitemap e prova de não publicação indevida; microcorreções só são válidas quando destravam essa vertical ou removem risco P0 comprovado.

Palavra de conveniência não enfraquece contrato. Ação pedida, documentada ou calculada com caminho seguro deve virar comando, dado, check, gerador ou coletor no repositório. Critério técnico só controla ordem, risco e validação proporcional; não permite omitir alta escala, demanda externa, fonte oficial, revisão, HTML leve, subagentes/ledger, dados permanentes ou continuidade.

Validação sem próxima execução calculada é passividade. Termos de conveniência devem ser lidos como critérios de gate, não como permissão para ignorar pedido explícito. Check verde com estado bloqueado deve ser convertido na próxima camada executável, no próximo dado permanente ou no próximo refinamento de algoritmo; verde bloqueado não é autorização para parar.

Pedido explícito do usuário é execução de laboratório, não orientação fraca. Caminho seguro no repo exige execução. Peça técnica ausente exige criar peça verificável, schema, coletor, teste, dado permanente bloqueado ou validador proporcional. O laboratório deve manter qualidade e publicação segura, mas não pode converter exigência do `/goal` em espera passiva.

Pedido explícito não depende de ser útil; utilidade já foi definida pelo contrato. O laboratório deve executar a maior camada segura, com hipótese, evidência, dado real e validação proporcional. Termo como "quando útil" só pode aparecer como critério técnico de classificação, nunca como autorização para omitir trabalho pedido.

## Comando global

`./tools/lab-cycle`

Esse comando combina:
- `./tools/go-modern test -count=1 ./...`;
- `./tools/go-modern run ./cmd/check all`, que cobre os checks nomeados sem repetir `./tools/go-modern test`;
- `./tools/generate-batch-drafts --samples-per-batch 10 --checked-at 2026-06-09`;
- `./tools/lab-term-draft`;
- `./tools/lab-content-quality`;
- `go run ./cmd/build public`;
- `go list -m all`;
- `git diff --check`;
- busca por residuos `.py` e `.pyc`.

Use `./tools/lab-cycle` como prova global em momentos críticos ou alterações de grande alcance. Não transforme esse comando em ritual automático para toda edição pequena: isso aumenta custo sem melhorar a prova. O checkpoint deve explicar por que a validação escolhida foi suficiente; se a validação global foi pulada, registrar os checks focados usados. O comando global não deve chamar `./tools/check-all` nem repetir checks individuais já cobertos por `cmd/check all`; duplicação sem ganho é falha de otimização.

`cmd/check all` deve usar `internal/checks.RunAll` para preservar a ordem de `checks.Names`, compartilhar contexto top-level e manter `Run(name, root)` compatível com execução isolada.

O gate `./tools/check-performance-budget` deve reprovar HTML publico pesado, `<script>`, runtime cliente, bundle JavaScript, WebAssembly, mapas, `modulepreload`, import map, marcadores de hidratacao e CSS inline excessivo. Leveza e parte da prova de indexacao para Googlebot e bots valiosos.

`./tools/check-http-smoke` valida o caminho HTTP real do servidor: home 200 e indexável, busca noindex, `robots.txt`, sitemap index, sitemap de páginas, content types e ausência de runtime cliente no HTML principal. Esse smoke cobre o que o build estático sozinho não prova.

`./tools/check-agent-context-ledger` valida que agentes auxiliares usados no ciclo foram registrados em `.agents/agent_context_ledger.jsonl`, com política `reference_only_no_repo_write` ou `delegated_repo_write_codex_validated`, sem escrita concorrente, com evidência, risco, decisão de integração, fechamento antes do checkpoint e validação obrigatória pelo Codex principal. `context_kept_open=true` não é escape para agente concluído ou integrado. Em ciclo atual, use `--require-cycle <ciclo> --require-run-id <run_id>` juntos para evitar falso verde por ledger histórico. Sem esse ledger, achado de subagente não conta como prova de checkpoint; escrita delegada sem validação principal reprova. A decisão de integração deve registrar resolução concreta no ciclo e não empurrar achado para "próximo ciclo" ou "futuro"; continuidade operacional fica em `handoff`.

`./tools/lab-content-quality` usa arquivos de execução em `/tmp` para validar texto natural versus texto mecanico. Isso e laboratorio, nao publicacao. Esses arquivos devem ser fixtures sintéticas recriáveis; se o teste usar termo, fonte, brief, rascunho ou decisão editorial real, o insumo e a decisão útil devem estar em camada versionada bloqueada. Ele deve detectar conteudo raso, keyword stuffing e permutacao antes que qualquer pagina seja exposta ao Googlebot.

`./tools/check-cpu-budget` vale para runtime publico/producao. Ele nao proibe testes, build, laboratorio, auditorias ou validacoes em massa mais pesadas quando forem necessarias para provar qualidade. No laboratorio, usar CPU de forma agressiva e aceitavel quando acelera score, refinamento, descoberta de falha ou prova de escala; o gate impede que caminhos de atendimento publico gastem CPU com execucao externa, rede, sleeps ou loops sem limite.

`./tools/lab-term-draft` usa seeds juridicas aprovadas pelo contrato de `term_seeds` para criar cópia de execução de laboratorio em `/tmp`. O rascunho deve ser `draft/noindex`, nao pode escrever em `content/pages.json`, nao pode entrar em sitemap e nao pode receber CTA. Rascunho autoral aproveitável, fonte, termo ou decisão editorial gerada pelo ensaio deve ser persistido antes de checkpoint em camada versionada bloqueada.

`./tools/persist-term-drafts` e ferramenta de ciclo para gravar rascunho validado na camada `editorial_drafts`; `./tools/check-editorial-drafts` e o gate permanente no laboratorio para garantir que o draft persistido continua fora da publicacao.

`./tools/queue-editorial-review` move rascunhos persistidos para fila de revisao `needs_review`, sem publicacao. `./tools/check-review-queue` exige `publication_allowed=false`, `public_path` vazio, fonte, autoria e historico.

`./tools/block-publication` cria manifesto de publicacao bloqueada; `./tools/check-publication-blockers` garante que aprovacao editorial ainda nao libera URL publica.

`priority-brief-candidates` passar significa que prioridades observadas foram copiadas para uma fila editorial bloqueada sem perder linhagem e sem sobrescrever briefs curados. Não significa brief aprovado, texto autoral, revisão jurídica, CTA público, rota, render, sitemap ou `published_manifest`. O gate deve gerar exatamente um candidato por prioridade observada, nenhum candidato para `needs_more_external_observation`, preservar observações/superfícies/consultas/fonte exigida, bloquear flags públicas e manter `content_briefs` separado. Se essa camada for lida como conteúdo pronto, trate como erro de contrato.

`priority-authorial-drafts` passar significa que cada candidato prioritário recebeu rascunho autoral interno bloqueado com linhagem, fonte oficial exigida, problema humano, documentos, triagem digital, CTA interno contextual e orçamento interno de title/meta. Não significa página pronta, publicação, rota, sitemap, CTA público, fonte resolvida para release ou revisão jurídica aprovada. O gate deve rejeitar texto fino, opening repetido, CTA sem `Origem`, `Intent` e `Documentos`, fonte não oficial, score fraco, orçamento de snippet fora do contrato e qualquer flag pública verdadeira. Se o title/meta só passa por corte artificial, se a abertura parece molde ou se a fonte continua ampla, a resposta obrigatória é refinar gerador, algoritmo e teste, não aceitar o verde.

`priority-source-specificity` passar significa que cada rascunho prioritário recebeu uma decisão bloqueada de fonte: referência oficial específica travada ou blocker acionável por fonte ampla/contextual. Não significa fonte liberada para publicação, revisão jurídica aprovada, rota, render, sitemap ou `published_manifest`. O gate deve reprovar contagem diferente dos rascunhos, identidade por `seed_term_id` em vez de `priority_authorial_draft_id`, URL não oficial, fonte ampla marcada como travada, política diferente de `reference_only_no_scraping_no_ingestion`, texto bruto armazenado, `publication_allowed=true`, `render_allowed=true`, `sitemap_allowed=true` ou `public_path`. Se uma fonte oficial específica for bloqueada por regra conservadora, o próximo passo é adicionar evidência/auditoria e teste negativo, não liberar por domínio.

`priority-legal-reviews` passar significa que a revisão jurídico-editorial prioritária foi calculada e persistida em camada bloqueada. Não significa aprovação OAB final, rota pública, CTA público, render, sitemap, `published_manifest` ou página indexável. O gate deve reprovar ausência de readiness, identidade que não venha de `content/site.json`, nota fina, required_fixes vazios, CTA sem origem, paid-intent bloqueado sem bloqueio explícito, `approval=true`, `publication_allowed=true`, `render_allowed=true`, `sitemap_allowed=true` ou `public_path`. Depois desse check, a próxima decisão deve ser release evidence/HTML leve/canonical/robots/smoke bloqueado ou expansão externa metadata-only, não parada.

Se a validação de expansão passar apenas porque registros foram derivados de dados locais, trate como falso conforto. O check deve deixar claro qual sinal externo ainda falta, qual coletor ou API precisa existir, que duplicidade semântica ainda pode passar, quais temas podem virar conteúdo jurídico próprio e quais permanecem bloqueados por baixa intenção, gratuidade, presencialidade dominante, fonte ampla ou risco de cópia.

Promocao de candidato para seed deve passar por ranking refinavel, nao por lista fixa. O score deve considerar area, risco, fonte oficial, adequacao digital, CTA WhatsApp e penalidades para fluxo presencial ou evidencia fraca. Quando falso positivo ou falso negativo aparecer, escrever teste e ajustar o algoritmo antes de continuar.

Todo ciclo de validação deve recalcular expansão e robustecer algoritmo quando houver evidência. Se conteúdo, title/meta, CTA ou rascunho final mudar, regenerar gates derivados e atualizar testes para os dados reais sem baixar exigência. Se uma falha aparece em mais de um lote, ela deve virar regra, comparador, score, fixture ou teste de contrato; não basta registrar que o check passou depois de um ajuste manual.

Rascunho autoral deve passar por algoritmo anti-template antes de qualquer novo lote: abertura repetida, conjunto de secoes reaproveitado, heading generico, CTA raso, fonte ausente ou path publico devem reprovar. Contagem de palavras isolada nao basta para liberar conteudo.

Se a inspeção mostrar grafia mecanica ou sem acento em rascunho PT-BR, tratar como falha de laboratorio. Refinar `internal/draftlab`, regenerar `data/editorial/drafts.jsonl`, atualizar `data/editorial/review_queue.jsonl` e rodar novamente os checks antes do commit.

A página usada no plano precisa ser derivada do rascunho autoral real e das camadas de revisão/fonte que chegaram ao gate; resumo sintético, corpo genérico ou fixture criada apenas para atravessar `publicrelease` deve reprovar. Passar nesse check prova coerência técnica somente quando o corpo autoral real também foi conferido; não prova aprovação Codex auditável, não escreve staging, não anexa manifesto e não autoriza swap/promoção.

Depois da promoção controlada bloqueada dos 181, rodar `./tools/generate-priority-final-sample-reviews` e `./tools/check-priority-final-sample-reviews`. Esse gate deve consumir rascunho autoral real, plano de manifesto, transação, fonte, CTA/OAB, paid-intent, HTML/SEO, risco de duplicidade e blockers finais; deve manter 181 registros bloqueados no estado atual, `approval=false`, `publication_allowed=false`, `render_allowed=false`, `sitemap_allowed=false`, `public_path=""` e notas de falso positivo/falso negativo. Passar nesse check prova leitura técnica bloqueada da vertical atual, não aprovação pública, não `published_manifest`, não sitemap real e não autorização de indexação. O próximo avanço deve partir desse gate: publicação pública aprovada somente se todos os requisitos finais forem cumpridos, lane informativa bloqueada ou expansão externa/conteúdo autoral de alta intenção com cadeia completa.

Depois de `priority-final-sample-reviews`, rodar `./tools/generate-priority-similarity-report` e `./tools/check-priority-similarity-report` quando a aprovação Codex auditável tiver métrica por registro. Esse relatório deve agregar os piores pares por global, seed e contexto, preservar o score máximo observado, explicar risco de falso positivo/falso negativo e manter `approval=false`, `publication_allowed=false`, `render_allowed=false`, `sitemap_allowed=false`, `public_path=""` e `index_policy=noindex`. Passar nesse check prova que o risco material ficou visível para triagem editorial em lote; não autoriza reescrita mecânica, publicação, sitemap ou relaxamento do limite.

Depois de `priority-similarity-report`, rodar `./tools/generate-priority-similarity-semantic-reviews` e `./tools/check-priority-similarity-semantic-reviews` para os pares de maior risco. Esse gate deve registrar contraste documental, fonte, risco humano, decisão editorial e ações exigidas antes de release, mantendo `approval=false`, `publication_allowed=false`, `render_allowed=false`, `sitemap_allowed=false`, `public_path=""` e `index_policy=noindex`. Passar nesse check não corrige conteúdo por si; ele calcula onde reescrita autoral real ou distinção jurídica mais forte precisa acontecer sem mascarar o limite.

Depois da exclusão comercial BPC/LOAS ou equivalente, rodar `./tools/generate-priority-informational-lane` e `./tools/check-priority-informational-lane`. Esse gate deve consumir os 8 registros excluídos por paid-intent, fonte oficial, rascunho autoral, revisão e promotability; deve manter `commercial_cta_open=0`, `approval=false`, `publication_allowed=false`, `render_allowed=false`, `sitemap_allowed=false`, `public_path=""` e documentos/avisos específicos do tema. Passar nesse check prova que a utilidade informativa foi preservada sem mascarar promoção comercial; não autoriza CTA público, render, sitemap, `published_manifest` ou indexação.

Antes de promoção controlada com staging ou espelho public bloqueado para os gates calculados, manter a guarda contra falso positivo da transação: o teste deve falhar se `priority_manifest_transaction_rehearsal` voltar a usar corpo sintético, a camada deve ser regenerada a partir de `priority_authorial_drafts`, amostras devem ser revisadas, o diff precisa continuar vazio em `public/`, `content/pages.json` e `data/editorial/published_manifest.jsonl`, e só então avançar para lock/rollback/smoke bloqueados.

Para a vertical prioritária atual, promoção controlada bloqueada dos 181 selecionados é prova técnica obrigatória, não publicação. `./tools/generate-priority-controlled-promotion` e `./tools/check-priority-controlled-promotion` devem consumir `priority_manifest_transaction_rehearsal`, preparar staging em raiz isolada recriável, rodar `MaterializeStaging`, `MaterializeTemporaryPublicPlan`, smoke HTTP/Googlebot bloqueado, plano de swap, lock, ledger, rollback e retorno obrigatório `public_release_promotion_blocked_by_default` ao tentar swap. O check deve reprovar qualquer `approval=true`, `publication_allowed=true`, `render_allowed=true`, `sitemap_allowed=true`, `public_path` preenchido ou alteração permanente em `.release-staging` real, `public/`, `content/pages.json`, `published_manifest` e sitemap real. Passar nesse check prova que a mecânica de promoção bloqueada funciona; não prova aprovação jurídica final nem autoriza `published_manifest`.

Se a similaridade subir em volume maior, investigar a semântica: verificar se os textos diferem em problema, documento, fonte, risco e ação digital. Não resolver similaridade com troca mecânica de palavras ou redução de limite.

## Politica

Nenhum script isolado e prova suficiente para mudanca P0/P1 ampla. Use o laboratorio como conjunto proporcional de provas e inspecione os artefatos quando a mudanca afetar HTML, sitemap, robots, canonical, indexacao, qualidade ou conteudo. Mudança localizada deve priorizar validação focada, desde que cubra diretamente o risco alterado.

Laboratorio verde nao autoriza mascarar bug de contrato. Antes de commit com conteudo, arquivo editorial, paid-intent, source-specificity, candidate gate ou strategy, revisar tecnicamente o contexto: diff, dados JSONL, motivo de blocker, amostras de texto, fonte, CTA e semantica da familia. Se houver falso positivo, falso negativo, dado stale, texto raso, similaridade suspeita, fonte ampla tratada como especifica ou conteudo comercial demais, corrigir algoritmo/teste/dado e rodar novamente. Nao baixar regra, nao remover blocker, nao renomear status nem aceitar "passou no script" como prova isolada.

Para expansão 10k+, checks de demanda precisam relatar cobertura proporcional ao backlog, não apenas mínimos absolutos. `demand-signal-observations` deve expor oportunidades observadas versus oportunidades totais, seeds cobertos, áreas/cenários/contextos cobertos e diversidade de superfície. Conjunto inicial pequeno de metadados pode continuar válido como camada inicial bloqueada, mas o relatório deve impedir leitura como demanda suficiente para escala ou como amostra textual aceita. Se só houver autosuggest Google/Bing, a próxima ação executável é criar ou operar uma superfície metadata-only adicional confiável, com política de uso, hash e flags públicas falsas.

O diagnóstico proporcional de `demand-signal-observations` deve aparecer na saída do check com `backlog_opportunities`, `opportunity_coverage_basis_points`, `observed_areas`, `observed_scenarios`, `observed_contexts`, `top_seed`, `top_seed_basis_points`, `top_area`, `top_area_basis_points`, `coverage_status` e `concentration_status`. `coverage_status=external_coverage_initial_needs_more_observation` e `concentration_status=external_demand_concentration_balanced_enough_blocked` são estados bloqueados válidos para laboratório, mas são comando de continuidade para ampliar metadados externos e preservar diversidade; não autorizam brief, rascunho, manifesto, render, sitemap ou publicação em escala.

Passar com `coverage_status=external_coverage_initial_needs_more_observation` é comando de continuidade, não checkpoint suficiente. A próxima fatia vertical deve criar ou operar nova superfície metadata-only confiável, persistir JSONL bloqueado e recalcular prioridades quando os metadados mudarem, salvo falha P0 comprovada que bloqueie a coleta ou validação.

O coletor de demanda externa deve aceitar superfícies metadata-only além de autosuggest sem copiar corpo de terceiros para a camada de observações. Para perguntas públicas, orgânico estruturado ou sinal social, `--public-questions-endpoint`, `--organic-results-endpoint` e `--social-trend-endpoint` devem capturar consulta, título/pergunta/sugestão, URL/hash, superfície, posição e política de uso. Quando a rodada declarar necessidade editorial de trecho textual, o corpo limitado deve ir somente para camada de amostras bloqueadas com limites e hashes próprios, operando `--capture-content-samples --require-content-samples --min-content-samples N`; se a superfície retornar apenas metadados, o estado correto é requisito textual não satisfeito com tentativa persistida. Antes de operar superfície textual nova, validar `demand-textual-surface-catalog` e ler `data/research/demand_textual_surface_catalog.jsonl`; catálogo verde não é amostra aceita, mas deve apontar próxima ação de conector, política e campos de payload. Teste verde de parser/CLI é pré-requisito, mas a evidência de escala exige operar a superfície permitida, persistir o JSONL bloqueado, ler amostras aceitas e tentativas falhas, e recalcular `demand_opportunity_priority` e a cadeia prioritária quando novos metadados mudarem cobertura, ranking ou riscos de gratuidade/presencialidade. Superfície bloqueada por segurança, limite opaco, parser quebrado, endpoint incompatível ou restrição de uso incompatível deve virar achado de engenharia e próxima correção executável, não dado forçado.

Antes de refinar algoritmo no laboratório, capturar dados reais do erro. Para similaridade, n-grama, título repetitivo, vazamento de área ou paid-intent suspeito, registrar ou imprimir o par/registro, `legal_area`, `source_matrix_id`, `unique_intent_id`, campos textuais e motivo de blocker. Ajuste sem essa evidência é chute e falha de contrato. Se o diagnóstico mostrar que o teste está certo, corrigir geração/conteúdo; se mostrar falso positivo, fortalecer o comparador sem baixar limite e mantendo teste negativo.

Validar nao basta. Todo ciclo deve revisar o diff, os artefatos gerados, os riscos e o contrato antes de commitar. A revisao deve procurar atalhos, spam, conteudo mecanico, regressao de P0 e dependencia indevida.

Antes de commitar, o agente deve fazer autocrítica explícita e registrar no checkpoint:
- o que este ciclo realmente resolveu;
- por que o commit não é conclusão do `/goal`;
- se existe pendência mascarada como entrega;
- se o diff público foi protegido quando aplicável;
- qual melhoria técnica ainda falta para a próxima camada vertical P0 e por que ela importa agora;
- qual risco de segurança, publicação, indexação, dado permanente ou regressão foi criado/reduzido;
- se a mudança reduz custo, tempo ou risco de forma real, ou apenas desloca complexidade para outro ponto;
- se a validação prova o comportamento certo, quais falsos positivos/falsos negativos ainda são plausíveis e que evidência reduziria essa dúvida;
- qual melhoria vertical P0 deve ser executada na continuidade imediata;
- qual é o próximo passo executável.

Essa autocrítica também é obrigatória em documentação de decisão, check ou gate criada/alterada no ciclo. A resposta não precisa repetir frases fixas; precisa ser concreta: apontar melhoria real possível, justificar segurança para rascunhos permanentes e publicação, separar otimização verdadeira de custo deslocado, avaliar risco de falso positivo/falso negativo na validação e indicar o próximo passo executável.

Commit sem plano de continuidade e sem autocrítica é inválido para este projeto.

Se qualquer validacao falhar:
1. identificar causa raiz;
2. corrigir;
3. rodar novamente;
4. registrar falha e correcao no checkpoint;
5. commitar checkpoint e artefatos do ciclo;
6. continuar imediatamente a próxima fatia vertical P0 quando nao houver bloqueio P0 real.

## Continuidade

O agente nao deve parar ao registrar checkpoint. Todo ciclo deve terminar com proximo passo acionavel, e esse proximo passo deve ser executado em seguida quando nao houver bloqueio P0 real comprovado. Checkpoint é marco de rastreabilidade, não permissão para encerrar o `/goal`.

## Commit por ciclo

Depois de validacoes relevantes passarem, fazer commit do checkpoint e dos artefatos do ciclo. O projeto nao deve depender de chat, contexto compactado ou memoria externa para continuidade.

Antes do commit, executar `date`, conferir a hora local e registrar o ciclo numerado no checkpoint. Isso mantem a ordem de auditoria mesmo apos compactacao de contexto.
